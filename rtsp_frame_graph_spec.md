# RTSP camera comparison tool

## Goal

Extend `rtsp_frame_graph.py` with a desktop GUI for monitoring one RTSP video stream or comparing two on one live graph, with an optional live video preview for each camera. The second stream is optional, and either camera slot can run on its own. The same Python application runs on Linux and Windows using PySide6, PyQtGraph, and PyAV. Each active camera uses one RTSP connection for analysis and live viewing. Preserve the existing single-stream command-line invocation, `python rtsp_frame_graph.py RTSP_URL`, and support it on both platforms. Launch the GUI with `python rtsp_frame_graph.py`.

## Window and controls

- Show two camera sections labeled **Camera A** and **Camera B**. Each contains an RTSP URL, an optional username, a masked password, and an independent connection status. Anonymous streams are supported. Accept credentials in the separate fields or in the URL. Reject conflicting credentials and percent-encode separate credentials when constructing the RTSP URL. Redact credentials from displayed errors and logs. Keep passwords in memory for the session and its retries.
- When a camera delivers its first valid frame, save its URL and username locally for that slot. Strip embedded login details and recognized secret query parameters from the saved URL. Prefill the saved fields on launch with an empty password field and the camera idle. Failed connections leave the last successful settings intact. An explicit command-line URL uses the credentials supplied in that URL.
- Give each camera its own **Start**, **Stop**, and **Restart** controls. **Start** validates that camera’s fields and starts its capture. Highlight invalid fields in that camera’s section. Leave an unused slot blank and **Idle**. A user can start the second camera at any time.
- Lock a camera’s connection fields while it is connecting, live, or retrying. **Stop** cancels that camera’s retries and ends its capture, then unlocks its fields. **Restart** cancels that camera’s retries, closes its current RTSP connection, and starts a fresh capture with the same settings. Offer **Restart** while that camera is connecting, live, or retrying. Each control affects only its own camera. Closing the window stops both cameras.
- Place **Start Both**, **Stop Both**, **Restart Both**, and **Live View Both** in a vertical stack to the right of Camera B. Each button invokes the corresponding available per-camera control on slots with a nonblank URL.
- Match each camera’s line color to its legend and summary. Use text for all statuses so color is optional for interpreting them. Append the video codec to the **Live** status, using H.264, H.265, or AV1 for those codecs. Each summary shows current smoothed bitrate, average capture FPS, total frames, I-frame count, and **MBs received** with the overall bitrate in Mbps in parentheses.

## Live view

- Add a **Live View** button to each started camera’s section. It opens a separate, resizable PySide6 window titled with the camera label. The preview has maximize and close controls and omits the minimize control because it shares the main window’s taskbar entry. Keep one preview window per camera and allow both to be open at once. Display the decoded source resolution and a text playback status in each window.
- Default to **Fit to window**, which shows the whole frame, preserves its aspect ratio, and refits as the window resizes. Offer **Actual pixels (1:1)**, which maps one decoded source pixel to one physical display pixel and accounts for display scaling. At 1:1, show scrollbars on each axis where the frame exceeds the viewport and support click-and-drag panning to every edge. Resizing the window changes the visible area while preserving 1:1 scale. Preserve the chosen mode and pan position as frames arrive. Clamp the position when the frame or viewport size changes and recalculate the mapping when display scaling changes.
- Render decoded PyAV frames in a PySide6 `QGraphicsView`. While the preview is open, publish frames through a bounded handoff that keeps only the latest frame. Perform any expensive image conversion off the GUI thread. If rendering falls behind, skip old preview frames and continue recording analysis data. Keep the graph and other camera responsive during 4K playback.
- Closing the preview unsubscribes it from decoded frames while capture continues. A camera’s **Stop** closes its preview. During **Restart** or automatic recovery, keep an open preview window and its view settings, clear stale video, show **Reconnecting**, and resume on the first new decoded frame. A display error appears in the preview and leaves capture running. Closing the main window releases both previews and captures.

## Live graph

- Use one graph with a shared elapsed-time axis starting at zero when a camera starts from a fully stopped or idle state. Starting the second camera while the first is active uses the existing time origin. Retain the latest 10 minutes of samples, follow the latest 60 seconds by default, and refresh every 500 ms during capture. Draw Camera A in blue and Camera B in orange. Show encoded frame sizes as thin impulses from zero on a square-root left axis. Label the ticks with the original frame sizes in KiB. Show exponentially smoothed bitrate as solid lines on a linear right axis with automatic units such as kbps or Mbps. Keep each axis scale shared between the two cameras.
- Drag the graph to pan horizontally and use the scroll wheel to zoom the time axis. Either gesture pauses automatic following. Keep a manually chosen range as samples arrive, clamping it when the oldest samples expire. **Back to Live** restores the latest 60 seconds. Draw the visible interval and mark both the peak and minimum frame sizes per horizontal pixel when zoomed far enough out to combine points. Allow navigation while captures are stopped.
- Timestamp compressed video packets on receipt and decoded frames on output using the same monotonic clock for both cameras. Once a valid frame has arrived, take bitrate samples at intervals of at least half a second. Divide the compressed video bytes received over each interval by the actual elapsed time. Plot each smoothed estimate at the midpoint of its interval, using a normalized, symmetric exponential weighting over up to 2.5 seconds on either side. Use a 2.5-second half-life for the exponential and taper its weight to zero at the cutoff. Emit the estimate once the future half of the window is available. During startup, use the available past samples. Keep frame-size points on their live timeline. For both bitrate and **MBs received**, count the size of each nonempty demuxed video packet once, before decoding. Display the cumulative total in decimal megabytes and divide its total bits by active capture time to calculate overall Mbps, excluding time spent stopped or reconnecting. The cumulative counter includes packets received during warm-up and packets that yield no decoded frame. It measures compressed video payload and excludes audio and network overhead. Count frames and I-frames from decoder output using the decoded picture type.
- When a stream is lost or stopped, discard pending bitrate points that still need future samples. Keep already plotted data until it scrolls out of view or the user starts a fresh capture in that slot. Reset the bitrate smoothing window for that camera on reconnect and show **Buffering…** when live until the first centered estimate is available. Show an em dash for current bitrate while a camera is disconnected. Keep byte, frame, and I-frame totals across automatic retries. The byte count holds steady while no video packets arrive and resumes with the first video packet after reconnect. **Stop** leaves the final totals visible. Compute average capture FPS over time spent receiving frames, excluding startup and reconnect gaps. **Start** and **Restart** reset the selected camera’s graph history, counters, and retry backoff.
- Pause automatic scrolling and retain the final history while neither camera is active. An unused slot counts as inactive, and an automatic reconnect keeps the graph updating. Starting either camera after the graph has frozen clears both sets of plotted points and starts a new timeline. The other slot keeps its summary totals until it starts a new capture.

## Graph exports

- **Start Recording** opens a file picker for a CSV and begins writing new graph points. Include the session number, camera, elapsed seconds, frame size in KiB, and smoothed bitrate in Mbps as columns. Write one point per row, with the unused value column blank. Use the same center timestamp for each bitrate point in the plot and CSV. Increment the session number when the graph resets. **Stop Recording** or closing the window flushes and closes the file. Recording stays enabled across camera stops and starts and adds no graph points while the graph is frozen.
- **Save Snapshot** opens a file picker for a PNG of the current graph with both cameras’ stats, statuses, and sanitized RTSP URLs. Use the URL that produced a camera’s current stats if available. Remove embedded login details and recognized secret query parameters from the displayed URL. Default both exports to a location outside the checkout.

## Per-camera connection status and recovery

| Status | When it appears |
| --- | --- |
| **Idle** | Capture has never been started in this camera slot. |
| **Connecting** | The initial RTSP connection is opening or waiting for its first valid video frame. |
| **Live** | The current connection has delivered a valid frame and the frame watchdog has yet to expire. |
| **Connection lost · retry in Ns** | A previously live connection ended or stopped delivering valid frames. Show the reason and time until the next attempt. |
| **Retry scheduled · in Ns** | An initial or subsequent attempt failed before receiving a valid frame. Show the reason and time until the next attempt. |
| **Reconnecting · attempt N** | A retry is starting or waiting for its first valid frame. |
| **Error** | A permanent local setup error requires action, such as a missing PyAV installation. Show the cause. |
| **Stopped** | The user stopped this camera and its capture has been cleaned up. |

1. Start a PyAV capture worker for each enabled camera. Only a valid decoded video frame marks the camera **Live** and resets its frame watchdog. Apply a 15-second deadline for the first valid frame, including connection setup, and a 5-second deadline since the latest valid frame once live. Treat end of stream and fatal demux or decode errors as immediate failures. Report a sanitized diagnostic when available.
2. On failure, close out the current graph segment, close the old RTSP connection, and schedule a retry only after cleanup. Retry with delays of 1, 2, 4, 8, 16, and then 30 seconds for each subsequent attempt. Continue while that camera is enabled for capture. Reset the backoff after 10 consecutive seconds of valid capture, so a stream that repeatedly connects and drops still backs off. Keep the retry count and timers independent for each camera.
3. Open a fresh PyAV input on each retry. Ignore late events from an old input or capture session. Keep at most one open RTSP connection per camera. **Stop** and **Restart** cancel pending retries for the selected camera immediately. Closing the window cancels both cameras’ retries. A failure, timeout, or retry for one camera leaves the other camera’s capture, status, and graph updates running.

## Capture and platform behavior

- Use PyAV to open RTSP over TCP with bounded open and read timeouts. In a worker outside the GUI thread, demux the first video stream and decode it once. Measure compressed packet sizes before decoding, collect frame metadata from decoder output, and forward those same decoded frames to any open preview. Use a GUI timer to update widgets and check watchdog deadlines even when reads stall. Stop and restart must cancel obsolete work, release the input and decoder in the owning worker, and keep the GUI responsive while cleanup finishes.
- For the frame-size plot, associate encoded bytes with decoded frames only when the mapping is unambiguous. Decoder buffering and reordering can change when a packet yields output, so use reliable timestamp or codec information where available. For frames without a reliable size, omit their impulses and indicate that some frame sizes are unavailable. Continue counting those frames and include all received video packet bytes in bitrate.
- Share capture and bitrate statistics between the GUI and CLI. Document dependency installation and supported RTSP codecs on both platforms. The GUI uses PyQtGraph, and the existing CLI may continue to use gnuplot. Use `ffprobe` as a reference tool for verification.

## Acceptance checks

- Connect both cameras, using separate login fields for one and an embedded login for the other. Relaunch and verify each slot restores its last successful URL and username with an empty password field and an idle status. Verify saved settings contain no passwords and a failed connection leaves the previous settings intact.
- On native Windows and Linux, start either camera with the other slot blank. Verify the selected camera plots normally and the unused slot stays **Idle**. Start the second camera later and verify both use the original time axis. Use authenticated test streams with different frame sizes and rates to verify the series colors, axes, prompt delivery of frame records, and independent first bitrate samples. Verify that frame-size points appear during bitrate buffering and that centered bitrate points are recorded at their plot timestamps.
- Disconnect one stream while both are live. Verify its status changes within the watchdog deadline or immediately on end of stream, its bitrate line develops a gap, and the other camera continues updating. Restore the stream and verify it returns to **Live** and resumes bitrate plotting from a fresh sample.
- Start with one working stream and one unreachable stream. Verify first-frame timeout, retry countdown, capped backoff, and independent operation of the working stream. Exercise repeated short reconnects and verify the backoff resets only after stable capture.
- With one camera live, stop the other during a retry countdown and again during an active connection attempt. Verify its RTSP connection closes, its retries are canceled, and the live camera continues plotting. Restart a camera while live and during a retry countdown. Verify exactly one fresh RTSP connection opens with the same settings and fresh counters, and the other camera’s history and counters stay intact. Close the window and verify both captures and retry schedules are cleaned up. Confirm diagnostics omit camera credentials and the original single-stream CLI still runs on both platforms.
- On Windows and Linux, preview a 3840×2160 test stream with a pixel grid on a 1920×1080 display. Verify **Fit to window** shows the full frame when resized. At **Actual pixels (1:1)**, verify pixel mapping at default and scaled display settings and reach all four corners using both the scrollbars and drag panning. Resize while panned and confirm the scale remains 1:1.
- Use an RTSP server that reports client sessions. Verify each active camera has exactly one connection with its preview open or closed, including when both previews are open. Interrupt and restore one camera and verify its graph and preview recover from the same new connection, with the preview’s view settings preserved. Close or deliberately slow a preview and verify measurement continues without dropped analysis data.
- Compare captured metrics with `ffprobe` on identical recorded test fixtures, including a stream with reordered frames. Check packet-byte totals, decoded frame and I-frame counts, and encoded frame sizes where the association is available. Verify ambiguous frame sizes are omitted and their packet bytes still contribute to bitrate.
- Verify each camera’s displayed **MBs received** and overall Mbps match its cumulative packet-byte total and active capture time. The total stays steady during an outage, resumes from its previous value on automatic reconnect, and remains visible after **Stop**. Verify **Start** and **Restart** reset only the selected camera’s total.
- Start, restart, stop, and open previews using the grouped controls with both URLs configured and then with one URL blank. Verify the controls skip the blank slot. Check the codec shown for H.264, H.265, and AV1, and verify the graph holds its final time range and data after the last camera stops and resets to zero on the next start.
- Record graph data across two capture sessions and verify the CSV distinguishes the sessions and contains both kinds of points. Save a snapshot while stopped and verify it shows the frozen graph, status, stats, and sanitized URLs, even if a stopped camera’s URL field has been edited since capture.
- Populate ten minutes of history. Pan and zoom the time axis, check that automatic following pauses, and verify **Back to Live** returns to the latest 60 seconds. Verify zoomed-out peaks and minimum sizes stay visible, old points expire, and the stopped graph remains navigable.
